The pattern

One repository, owned by the person the site is for.

A sovereign agentic website is a repository the owner controls, holding the site as plain files, its content and its schema, the instructions for the agents and the behaviour policy that limits them, with checks and a deploy that run on any host.

Each part below is there for one reason: so that the site belongs to its owner, and agents can work on it without taking that away.

1. A repository the owner controls

The site lives in the owner's own repository, with its history. Every change is a commit, and every version can be restored. Nothing of the owner's has to be kept by anyone else: if the people who set it up were bought, or disappeared, the owner would already hold everything.

The hand-over is one sentence: here is your repository; point your own AI at it, and start editing.

2. The site as plain files

The site is static: files, built once and served as they are.

  • No server code running, no database, no plugin to patch, and no login page on the site itself to attack.
  • No cookies unless the owner adds them, so nothing to put behind a banner, and no tracking by whoever built it.
  • Served from any static host: GitHub Pages, for free, or any web host.

The static design removes a whole category of flaw, code running on a server. That is an argument, not a measurement: no study we know of measures how much safer static sites are. Read more in static against the platforms.

3. Content and schema

The structure of the site and its content are files in the repository, in open formats, which the owner's own AI can read and change. This matters as much as the code: an export in a format the vendor chose is access, not control. Owning the schema is one of the four tests of sovereignty.

4. CLAUDE.md for the agents

A CLAUDE.md at the root of the repository is written for whoever works on the site, the owner and their agents: what the site is, how to change words and photos, which checks run, and what not to touch. The owner changes the site by talking to their own AI, not to a platform, and the AI starts from those instructions.

Because it is an agent doing the editing, the site can do whatever that agent can connect to: a new page, a rewritten section, a feed from another system.

5. A behaviour policy that limits the agents

An agent behaviour policy says what any agent working on the site may and may not do. It is a file in the repository, so the limits are written down, and checks can hold the agents to them rather than relying on memory.

The SovereignWebsite__Factory repository is a working example. Its policy/abp.json lists what each agent may change, what each pipeline may do, and every privilege its automation holds, with the reason; anything not listed is refused. An abridged excerpt:

"org-apply": {
  "allowed": ["repo.create", "repo.update_settings",
              "pages.enable", "pages.enforce_https", ...],
  "refused_always": ["repo.delete", "repo.transfer",
                     "repo.archive", "repo.make_private", ...]
}

In that repository, changes to the policy itself, to the workflows and to the build scripts take effect only when the owner merges them. The agents can propose; the owner decides.

6. Checks and a deploy that run on any host

Before anything goes live, checks run on every change. In the examples the pattern comes from, they include a build, validation, a leak scan for anything private, and, in the Factory, a check that every commit is signed and only touches paths the policy allows. Then the deploy publishes the files.

Because the site is plain files, the deploy is not tied to one provider: the same files serve from GitHub Pages or any web host. This site is built that way too: it is plain files in a repository, published by a short GitHub Pages workflow.

A static site is not automatically safe. An owner's AI could publish something private, embed a script from somewhere unsafe, or break a page. That is why the pattern carries guard rails, the policy and the checks, and why every change is a commit that can be undone.

What this does not claim

  • This is a description of the pattern, not a finished specification; the pattern's repository is still to be set up.
  • The examples named here use GitHub and Claude; the pattern itself is plain files, a policy and checks, meant to run on any host.
  • No security figure is claimed for static sites.
